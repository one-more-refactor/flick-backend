## 2026-03-02 - Length-based Timing Leaks in Custom Bearer Token Comparisons
**Vulnerability:** The previous implementation of administrative bearer token comparison `constant_eq` had an early-return optimization when the length of the expected token and the given token differed (`a.len() == b.len()`). This created a timing leak that allowed an attacker to determine the precise length of the secret `FLICK_ADMIN_TOKEN` by measuring response latency.
**Learning:** While custom constant-time comparisons like a loop of XOR operations are common, checking length equality first exposes a subtle timing side-channel. Additionally, hand-crafted comparison loops in Rust can be optimized away or restructured into branching logic by modern compiler backends (like LLVM).
**Prevention:** To prevent length and byte-by-byte timing side-channels, always hash the variable-length secret and input tokens to a fixed length (e.g. using SHA-256) before performing comparisons, and employ heavily-audited, timing-attack-resistant cryptographic libraries (like `subtle`) rather than rolling custom loops.
